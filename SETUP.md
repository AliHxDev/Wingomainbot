# WinGo WhatsApp Signal Bot

A single-service production deployment for Render that combines an Express API, React dashboard, PostgreSQL persistence, Baileys WhatsApp pairing-code authentication, WinGo 1M polling, deterministic signal generation, and signal result tracking in one Node.js process.

## Architecture

- `server/index.mjs` starts the HTTP API, database migration, WhatsApp manager, and WinGo signal engine.
- PostgreSQL stores admin users, settings, WhatsApp authentication state, channel recipients, bot state, signals, and result records.
- `server/services/whatsapp.mjs` owns exactly one Baileys socket at a time and persists auth state in PostgreSQL rather than a local disk directory.
- `server/services/wingoApi.mjs` fetches and normalizes WinGo history with timeout/retry/malformed-payload handling.
- `server/services/predictionEngine.mjs` combines deterministic recent-result analyses into size/color predictions and a 0-100 confidence score.
- `frontend/` is a Vite React SPA; the production build is written to `public/` and served by Express.

## Local installation

Requirements: Node.js 20.18+ and PostgreSQL 14+.

```bash
cp .env.example .env
npm install
npm run build
npm start
```

Open `http://localhost:10000/`. On first launch the setup wizard creates the first admin account. After setup, sign in with that account.

For development with the same Express-served frontend workflow, build before starting the server. The backend serves the built SPA from `public/`.

## PostgreSQL

Set `DATABASE_URL` to a normal PostgreSQL connection string. The server automatically creates required tables and indexes at startup using an advisory lock, so no external migration runner is required.

Render PostgreSQL connections are accepted through the same `DATABASE_URL`. SSL is automatically enabled by the server when `NODE_ENV=production` unless the connection string explicitly disables SSL.

## Render deployment

The included `render.yaml` defines one **always-on Web Service** only. It installs dependencies, builds the React dashboard, and starts `server/index.mjs`. No Render Background Worker, Vercel app, paid WhatsApp API, or persistent Render disk is required. The blueprint uses Render's `starter` web-service plan so the polling/socket process is not intentionally put to sleep; the plan can be adjusted separately if you accept intermittent sleep.

Create a Render PostgreSQL database and place its connection string into the web service's `DATABASE_URL` environment variable. `JWT_SECRET` is generated by the Render blueprint. Deploy the repository using the included `render.yaml`.

After the deploy is healthy, open:

`https://YOUR-RENDER-SERVICE.onrender.com/`

## First-time WhatsApp setup

1. Create the admin account in the setup wizard.
2. Open WhatsApp setup and enter the phone number that will own the bot in international digits-only format, for example `923001234567`.
3. Click **Generate Pairing Code**. The backend asks Baileys for a pairing code; no QR authentication is used.
4. Enter that code in WhatsApp on the target phone under **Linked devices**.
5. After the connection becomes `open`, configure one or more WhatsApp recipient JIDs. Contacts are accepted as digits-only phone numbers and are normalized to `number@s.whatsapp.net`. Groups may be entered directly as `123...@g.us`.
6. Start the bot from the dashboard.

The bot stores Baileys credentials/keys in PostgreSQL, which avoids dependence on a persistent Render disk.

## Channel configuration

The dashboard calls this destination list “channel configuration”. A recipient can be:

- `923001234567` for a WhatsApp contact.
- `123456789012345678@g.us` for a WhatsApp group.
- A valid Baileys-supported JID when you already know it.

Recipients are stored in PostgreSQL. Signals are sent to all configured recipients.

## Signal engine

The engine polls the WinGo 1M history endpoint every 60 seconds by default. Each newly observed result settles any matching pending signal and updates WIN/LOSS statistics. Then the engine evaluates recent history and predicts the next issue only when its deterministic confidence reaches the configured threshold (65% by default).

WinGo rules implemented by the application:

- `0-4`: SMALL
- `5-9`: BIG
- `0`: RED + VIOLET
- `5`: GREEN + VIOLET
- even non-5/non-0: RED
- odd non-5/non-0: GREEN

The predictor combines 3-gram pattern continuation, trend reversal, weighted moving-average pressure, recent-result weighting, frequency analysis, and independent Big/Small and Red/Green trend signals. Confidence is an analysis score, not a guarantee of a winning result.

## Troubleshooting

### Dashboard returns 503 on startup

The database is not ready or `DATABASE_URL` is invalid. Check Render service logs and confirm the database is reachable.

### Setup wizard says setup is unavailable

An admin account already exists. Sign in instead; the setup endpoint is intentionally one-time.

### Pairing code fails

Make sure the phone number is the WhatsApp account's full international number without `+`, spaces, or punctuation. A previously authenticated socket may also already be connected; use **Reconnect** after checking status.

### WhatsApp disconnects

The manager reconnects closed sockets with bounded exponential backoff. A logged-out session clears its persisted auth state and requires a new pairing code.

### No signals are sent

Verify all of the following in the dashboard: WhatsApp status is `open`, at least one recipient is configured, the bot is started, WinGo history is reachable, and your confidence threshold is not above the engine's current confidence.

### Render restarts and WhatsApp remains linked

Credentials are kept in PostgreSQL. A process restart recreates the socket from the saved state without relying on local disk persistence.

## Production notes

Use a strong unique `JWT_SECRET`, keep the dashboard behind HTTPS, and restrict database access to the Render application where possible. The application does not promise or market guaranteed profits; prediction confidence is only a deterministic model score.
